# 验收方法论（MEASUREMENT）

> 这个项目的核心资产不是补丁，是**怎么判断它到底修好了没有**。
> 补丁可以被抄走，判据抄不走 —— 而抄走补丁不懂判据的人，会把相机搞坏。

---

## 1. 为什么需要一套方法论

最初我们以为"分段连续 = 录像连续"。

**错得很彻底。** 实测反例：

| 指标 | 状态 | 真实情况 |
|---|---|---|
| mp4 文件名 | 连续 | ✅ |
| 分段数（每分钟 6 段） | 满 | ✅ |
| Frigate `recordings` 表 | 无空洞 | ✅ |
| go2rtc `recv` 累计字节 | 单调 | ✅ |
| **mp4 内部视频帧** | — | ❌ **4~8 秒无帧** |

空洞写在**单个 mp4 内部**，所有外层指标都看不见。用户看到的"画面跳一下"就是这个。

所以判据必须下沉到 **帧级**。

---

## 2. 三层判据

```
┌─ 第 1 层：连接层（相机侧自证）────────────────────────────┐
│  p5（干净断链次数）/ teardown / 队列满丢帧计数              │
│  判据：全部为 0                                            │
│  来源：rRTSPServer 自己的日志                              │
└────────────────────────────────────────────────────────────┘
┌─ 第 2 层：传输层（字节是否忠实）──────────────────────────┐
│  同窗 wire / mirror 的 IDR 逐字节 A/B                      │
│  判据：byte-exact 比例 = 100%                              │
│  来源：h264_capture_audit.py + idr_ab_audit.py             │
└────────────────────────────────────────────────────────────┘
┌─ 第 3 层：画面层（用户到底看到什么）──────────────────────┐
│  跨分段拼全局帧时间轴，找相邻帧间隙                          │
│  判据：max_gap ≤ 0.100s，无 >1s 空隙                       │
│  来源：frame_gap_audit.py                                  │
└────────────────────────────────────────────────────────────┘
```

**三层全绿才算 PASS。** 任何一层单独绿都可能假阳性。

## 3. 五个测量陷阱（都是踩过的）

### 陷阱 1：`setts` 会把重连抹成完美 CFR

`-bsf:v setts` 按**输出包序号**重建时间轴。go2rtc 重连导致的丢帧/重叠，
被重新编号后看起来是完美连续的 20fps。

→ **看 PTS 审计时，必须同时看**：
- 视频包数是否落在合法段长（210 帧/段 ±容差）
- 是否有**同 mtime 的双文件**（双写重叠的指纹）
- go2rtc 日志是否有 `i/o timeout`

### 陷阱 2：Frigate API 403 会变成静默假 PASS

不带 `User-Agent` 请求 Frigate API 返回 403，脚本拿到空列表 → 判定"零空洞" → PASS。

→ 所有 API 调用**必须带 UA**，且**校验响应体非空**。

### 陷阱 3：`signalstats YDIF` 判花屏会双向失效

帧间差突刺判据（`YDIF > 3.0 AND YDIF > 8×median`）：

- 近距快速运动 → **误报**成花屏
- 持续静态竖向拉丝 → **漏报**（每帧都一样，没有突刺）

据此写过的"绿屏已根治""−95%"结论**已全部撤回**。

→ 改用空间梯度判据（`mean|dI/dx| / mean|dI/dy| ≥ 1.4`，320×180 灰度、每段抽 3 帧）
→ 且必须**配合目视抽帧**，自动判据只作初筛。

### 陷阱 4：`ptrace` 采 PC 会拿到缓存的假地址

首次 attach 后连续 `GETREGS`，999 个样本全是同一地址（缓存）。

→ 必须**循环 attach/detach** 采样。

### 陷阱 5：单向样本会把映射判反

P24 第一次做通道过滤时，只采到单向 SPS，把 1080p/low 的 type 映射判反，
整版上线后全错。

→ **关键结论必须有双向样本对称验证**（20/20 SPS 才算定案）。

## 4. 工具

### 台架（采样 + 注入 + 连续观察）

| 工具 | 作用 |
|---|---|
| `rtsp_stall_client.py` | 真实 RTSP/TCP interleaved 会话 + 慢消费者注入（`SO_RCVBUF=4096` 后停读） |
| `quant_stall_ab.py` | 双轨 1s 采样 + 4 秒后受控注入，出 `timeline.csv` |
| `continuous_watch.py` | 无注入连续观察，出 PASS/FAIL（`--minutes 20`） |
| `live_gap_monitor.py` | 实时空隙监控 |

### 画面尺子

| 工具 | 作用 |
|---|---|
| `frame_gap_audit.py` | 跨分段拼全局墙钟帧时间轴，找相邻帧间隙（**最终判定依据**） |
| `h264_capture_audit.py` | 自建 RTSP 会话把 RTP 重组为 Annex-B，判定损坏在哪一层 |
| `idr_ab_audit.py` | 同窗 wire / mirror IDR 逐字节 A/B |
| `streak_audit.py` | 空间梯度判据测静态竖向拉丝（**可信**） |
| `concealment_audit.py` | `signalstats YDIF` 突刺（**仅参考，不下结论**） |

### 窗口验收

| 工具 | 作用 |
|---|---|
| `p18_final_audit.py` | 窗口关闭后一次性权威全量审计 |
| `p18_production_monitor.py` | 低频验收：相机侧主动断链增量 |

## 5. 判据阈值速查

| 对象 | 阈值 |
|---|---|
| 相机出口塌陷 | `wlan0` tx `< 15 KB/s` |
| 消费端静默 | go2rtc `recv` `< 5 KB/s` |
| 消费端恢复 | `> 20 KB/s` |
| 分段容器时长 | `duration ≤ 11.5s` |
| 音轨首包 PTS | `≤ 0.5s` |
| 每段帧数 | `video ≥ 150`，`audio ≥ 100` |
| 正常 RTP 时间戳 | 恒 `0.050s`，sub-10ms 占比 0 |
| wallclock 指纹 | 大量 `0.1~20ms` 突发簇 + 偶发 `1~2s` 空洞 |
| 拉丝 | `mean|dI/dx| / mean|dI/dy| ≥ 1.4` |

## 6. 标准验收流程

```bash
# 0. 部署后等 5 分钟稳定
# 1. 开监控（窗口内不动任何配置）
./verify/p18_production_monitor.py 1800 /tmp/audit/monitor.log

# 2. 窗口关闭后，全量帧级审计
./verify/p18_final_audit.py <START> <END> /tmp/audit/final.txt "<DEPLOY_TS>"

# 3. 三态判定
./verify/verdict.sh --audit /tmp/audit/final.txt
```

`verdict.sh` 的判定逻辑：

```
PASS  = 相机侧 p5=0 AND teardown=0 AND drop=0
      AND 帧级 max_gap ≤ 0.100s AND 无 >1s 空隙
      AND 解码错误 = 0
CHECK = 相机侧全 0，但画面层有孤立异常（通常是 go2rtc 重连造成）
FAIL  = 相机侧非 0，或帧级出现成簇空隙
```
